> 目的：0.6.1 发布前用**自己的真实使用数据**找缺陷，而不是靠想象。

## 2. 本轮找到并修掉的真缺陷（错误面）

每条都满足：**真实触发 → 有量化依据 → 有失败路径测试 → 有变异验证**。

### F04 `code_task` 的 `next_action` 指向读不出来的目标（最严重）

**现象**（R21 产物实测）：

| goal | 推荐目标 | 照做结果 |
|---|---|---|
| 让 outline 支持 python | `embedded-reader.js::outline` | `SYMBOL_NOT_FOUND` |
| 把 trace 的默认值改一下 | `scripts/dev-collect.sh::MALONG_TRACE` | `AMBIGUOUS_SYMBOL` |
| 修改 buildOutlineNode 的结构 | `buildOutlineNode`（真符号） | 正常 |

根因：`best_production` 的判据是「生产档位 + 有 token 证据」，
但 **`kind=content`（注释里出现的词）同时满足这两条**；
它的 `name` 不是符号，推荐成 `locator` 必然读失败。
第二类：shell 里没有 `symbol_id` 的变量，同名多处 → `AMBIGUOUS_SYMBOL`。

**修法**：新增 `readableLocator()` —— 有 `symbol_id` 才按符号读，
否则退化为读整文件（`file_path` 读取恒定可用）。
`best_production` 优先取真符号，没有符号候选才退回 content 行。

**验证**：5 个 goal 全部可执行（修前 3 个中 3 个失败）。
测试 `test-task-next-action-executable.js`（16 断言）；
变异 M16b/M17b 均变红。

### F05 装载期 `tools/call` 被当成失败（约 40% 概率）

**现象**：新进程 `initialize` 完成后**不发 `tools/list`**、直接 `tools/call`，
5 次里 2~3 次拿到 `-32000 Server still loading modules`。

根因：`tools/list` 有 `waitForReady()` 排队等待，`tools/call` 却**直接报错**。
同一个"还没装完"状态，两种待遇。

更值得注意的是：仓库里至少有 3 个测试**在客户端侧重试**来绕开它
（`test-ac21-write-conflict` / `test-ac27-crash-window` / `test-ac20-request-id`），
所以这个缺陷长期没被发现——**测试替产品兜了底**。

**修法**：抽 `waitForReadyThen(id, run)`，`tools/call` 也排队等就绪（上限 15s 后兜底报错）。

**验证**：8 个新进程连续冷调用 **8/8 成功**（修前 5 次里 2~3 次失败）。
测试 `test-tools-call-before-ready.js`（5 次冷启动）；变异 M18 变红。

### F06 `old_string` 不存在却报"假成功"（会让人以为改完了）

**现象**：

```
code_patch({patch: {old_string: 'NOT_THERE_XYZ', new_string: 'x'}, dry_run: false})
→ ok=true, committed=true, effect="workspace_write"
→ summary "Applied edit to src/app.js (already present)"
→ 磁盘一个字节都没改
```

根因：幂等判据是「`new_string` 在文件里出现过」。
单字符的 `new_string`（`'x'`、`'}'`）在全文件必然命中 →
任何 `old_string` 拼错都被判成"已应用"。

**修法**：抽出唯一判据 `patchLooksAlreadyApplied()`：
`old_string` 与新串去空白后都要 ≥2 字符，且新串不能是旧串的碎片。
单写路径与 `code_batch` 组预检**共用同一函数**——
自用实测：单写修好后 `code_batch` 仍然假成功，正因为旧实现两处各写了一份。

**验证**：`test-patch-no-fake-success.js`（13 断言，含 batch 路径）；
变异 M19（撤销判据）/ M22（batch 恢复 `committed:true`）均变红。

### F06b `code_batch` 无变化批仍报 `committed:true`

**现象**：`no_effect:true` + `unchanged_files` + **`committed:true`** 同时出现——
"什么都没提交"与"已提交"自相矛盾，轨迹里 `state_commit` 也被带偏。

**修法**：`noEffect` 时 `effect='no_change'`、`committed=false`、`state_commit='not_attempted'`。

### F07 轨迹聚合把"上限"冒充成"真实值"

**现象**：

```
建议 next_action 未被调用: 20      ← A 池
建议 next_action 未被调用: 20      ← B 池
```

两个池完全相同，很可疑。查代码：`signals` 只留 `slice(0,20)` 样本，
打印用 `.length` → **超过 20 恒显示 20**。

**真实值**：A 池 **66**，B 池 **192**。严重程度差 3 倍，却显示成同一个数。

**修法**：新增顶层 `counts` 给真实总数，打印优先用它并标注"样本列前 N"；
`signals` 保持数组形状不变（向后兼容既有调用方）。

**验证**：`test-trace-triage.js` 新增 ①b 用例（造 25 条，断言 count > items.length）；
变异 M20 变红。

### F08 `VERSION_CONFLICT` 文案断言"外部改的"，还藏起了更优路径

**现象**：

```
message: base_version mismatch: FILE_CHANGED
suggestion: "File changed externally; re-read (read_symbol) and retry..."
```

但真实分布里最常见的是**调用方自己上一次写入**让 base 变旧
（B 池实测：`code_patch` 成功后 5~7 秒内就撞 `VERSION_CONFLICT`）。
而写回执里其实已经给了可复用的 `write_read_refs`（`wbase_*`）——实测直接可用。

**修法**：文案改为"可能是外部改，也可能是你自己刚写的"，
并明确指出可复用 `wbase_*`，不必重新 `code_read`。

**验证**：`test-dogfood-r15.js` 新增 2 条断言（必须提到 `wbase_*`、不得无条件断言外部改）。

### F09 二进制文件报成"还没索引"，并建议一条走不通的路

**现象**：对 `src/bin.dat`（含 `0x00`）调 `code_query(mode=outline)` →
`FILE_NOT_INDEXED` + `"Call reindex(...) to index it"`。
但解析器只吃代码语言，`reindex` **永远不会**索引二进制文件——
用户会照着建议白跑一轮。

**修法**：新增 `BINARY_NOT_INDEXABLE`，并直说 `reindex will NOT help`。
文档（`.md`）与代码文件的归因保持原样。

**验证**：`test-file-arg-binary.js`（10 断言，含"不得再给 Call reindex"）；变异 M21 变红。

### F10 `task_not_found` 的归因指错了方向

**现象**：B 池 14 天 **20 次** `task_not_found`。逐条核对**上一次 `code_task` 的时间差**：

```
最短 260s，最长 38855s（约 10.8 小时）
```

没有一条是"编造 id"。真实成因实测确认：

| 情形 | 结果 |
|---|---|
| 同 `MALONG_STATE_DIR` + 新进程 | ✅ 任务可复用 |
| **换了 `MALONG_STATE_DIR`** | ❌ `task_not_found` |

任务按 state dir 隔离（`entry-store` 的 `baseDir`）。
opencode 用 `~/.config/malong`、dsh 用 `~/.local/state/malong-dsh`，
换宿主/换 profile 就看不见——但旧文案一口咬定"不要编造 task_id"。

**修法**：无活跃任务时说明"任务按 `MALONG_STATE_DIR` 隔离（附当前值），
换宿主/换 profile 会看不见"；保留"不要编造"这句（它是另一类真实误用）。

**验证**：`test-s1-entry.js` 新增 1 条断言（必须点出 state dir）。

### F11 `edit_transaction` 是 13 个工具里唯一不带 `ok` 的

13 个工具都走 `envelope()`（自带 `ok:true`），只有 `edit_transaction` 不走：
成功回包只有 `status`/`txnId`/`files_changed`，失败回包只有 `error_code` ——
**成功与失败都没有 `ok`**。统一按 `ok === true` 判断的调用方会把成功当失败。

**修法**：唯一出口纯增量补齐（`ok` 缺失时按有无 `error`/`error_code` 判定），既有字段一个不动。

**验证**：`test-edit-transaction-ok-field.js`（15 断言，含 undo 后字节还原、失败路径必须 `ok:false`）；
变异 M23 变红（7 条）。

## 3. 行为面：不看错误，只看「人怎么用它」

错误码只说明「哪里炸了」。轨迹还能回答另一类问题：**工具的设计假设与真实用法差多远**。
下面全部由 TRACE v0 的元数据聚合得出（无参数、无源码），每条都给了可复跑的算法。

### 3.0 总账：它在被当「改码工具」用，不是「浏览工具」

写操作（`code_patch` / `code_batch` / `edit_transaction`）占 B 池 453/667 = **68%**，
读只占 130/667 = 19%。这解释了为什么本轮 9 个缺陷里 5 个落在写路径与错误归因上。

响应体量（`output_chars` 合计，token 成本代理）：

```
B 池 667 次调用 → 2466 KB ≈ 631k tokens
  code_batch      880.8 KB (36%)
  code_patch      549.5 KB (22%)
  code_read       373.5 KB (15%)
  code_task       285.0 KB (12%)
  edit_transaction 172.0 KB (7%)
```

`>15KB` 的调用只占 3%，却吃掉 15% 的总量 —— 都是写路径的大回包。

### 3.1 `edit_transaction` 一半以上的调用只是「事务骨架」★本轮修复 F14

用 `output_chars` 指纹反推动作类型（已用实测标定：`begin`≈84、`edit`≈638、`commit`≈2216）：

| 池 | 总调用 | begin | commit | 真 edit | 骨架占比 |
|---|---|---|---|---|---|
| A | 69 | 18 (26%) | 17 (25%) | 28 (41%) + 6 错误 | **51%** |
| B | 139 | 40 (29%) | 49 (35%) | 35 (25%) + 15 错误 | **64%** |

最长的一段是 **23 次连击**里 4 次 begin + 4 次 commit，只有 9 次真编辑。

**为什么这算缺陷而不是用法问题**：实测连续 `begin` 会**静默新建空事务**——
不报错、不复用、不提示前一个还开着（`listTransactions` 里能查到多份 `state=staged` 的孤儿）。
调用方看不到「你已经有一个开着的事务」，于是每改一处就再开一个。

**修法（F14）**：`begin` 时先查未提交事务，有就明确列出 + 给出复用路径
（`action=edit` 带那个 `txn_id`，或 `action=edit_multi` 一次装多个文件）。
仍允许新建（append-only 语义不变），但不再静默。
测试 `test-txn-begin-uncommitted.js`（12 断言）；变异 M24 变红（5 条）。

**还有一处横向不一致（F15）**：`code_patch` 从第 2 次起就给 `batch_hint`
（"submit them ALL in ONE code_batch"），而 `edit_transaction` 明明有 `edit_multi`，
却**从不提示**。同一种「一处一处改」的浪费，两个入口一边提醒一边不提醒。
实测：`edit` 连做 3 个文件，回包里一次 `edit_multi` 都没出现。

**修法（F15）**：同一事务内已 stage ≥2 个文件时给 `batch_hint`，
点名 `action=edit_multi` + 给出 `file_edits` 形状。阈值与 `code_patch` 对齐（第 2 次起），
只 1 个文件时不说 —— 避免变成噪声（本轮教训：建议要匹配真实节奏）。
测试 `test-txn-edit-multi-hint.js`（10 断言）；变异 M25（撤销）/ M26（阈值失效）均变红。

### 3.2 `code_check` 建议的粒度与真实节奏差 29 倍

| 指标 | A 池 | B 池 |
|---|---|---|
| 被建议 `code_check` | 64 次 | 180 次 |
| 实际执行 | **0 次** | **9 次** |
| 采纳率 | 0% | **5%** |
| 两次检查之间平均连写 | 32.5 次 | **29.4 次**（p90=125，max=168） |

再算成本：一次 `code_check(checks:['test'])` 实测 p50 = **59 秒**、平均 46 秒，
而一次写平均 929ms → **一次检查 ≈ 49 次写的耗时**。
若 180 次建议全部照做，额外耗时 **7856 秒 = 现有全部工具耗时的 540%**。

**结论**：不是用户不听建议，是建议的**粒度**和真实工作节奏差一个数量级。
`code_patch` 成功后在**第 1 次写**就催跑全量测试，而人（和 agent）的实际节奏是
「连写一批、统一验一次」。

**为什么不改**：试过一版「前两次写建议 typecheck（更便宜）」，
但实测本仓库无 `tsconfig.json`，`code_check(checks:['typecheck'])` 只返回
`analysis_only` + `stages: []` —— **106ms 的假安心，什么都没验**。
给人一条走不通或没意义的建议，比不给更糟（正是 F04 的教训）。
正确做法要先有「什么规模的改动值得跑哪一档检查」的基准，本轮不拍脑袋改。

### 3.3 三段式写链本可合并（真实可省的往返）

按「中间没有读/查打断的一串写」分段：

| 池 | 段数 | p50 | p90 | max | ≥5 次的段 | 其中只用同一个工具 |
|---|---|---|---|---|---|---|
| A | 29 | 2 | 17 | 23 | 9 | 4 段（可省 57 次往返） |
| B | 136 | 2 | 7 | 23 | 29 | 14 段（可省 122 次往返） |

按每次写平均耗时估：A ≈ 42 秒、B ≈ 113 秒的工具耗时（不含模型往返开销本身）。
这些段本可用一次 `code_batch` / `edit_multi` 装完。

**为什么不改**：这是**用法**问题，不是工具缺陷 —— 三个入口都支持批量。
真要改，属于「怎么把批量的性价比讲清楚」的文档/提示问题，且需要先确认
用户是「不知道能批量」还是「故意一处一处来」（轨迹看不出动机）。

### 3.4 `code_task` 慢调用的真实分布（不是均匀慢）

```
B 池 35 次 code_task：<1s 21 次、1-5s 9 次、5-30s 0 次、30-100s 1 次、>100s 4 次
```

是**双峰**：正常路径不到 1 秒；少数几次 114~157 秒。
慢的那 5 次全部发生在「距上次调用很久」（130s ~ 14 小时）之后，
且 `active_requests=1` —— 与「工作区索引被 GC / 换 workspace 后全量重建」一致
（`MALONG_WS_GC_DAYS` 默认 3 天）。

注意 `latency_ms` 的口径：`_traceT0` 在 `semaphore.acquire` **之前**打，
所以它含排队时间；而 120s 硬超时只覆盖执行阶段。
理论最坏 = 60s 排队 + 120s 执行 = 180s，观测到的 157s 落在这个窗口内。

**为什么不改**：需要先定「多久算慢、要不要进度反馈」，属于体验设计。

### 3.5 超时机制：机制成立，但有一个真实盲区（已记录，未改）

本轮一度把「157s + ok」当成「硬超时失效」的证据，深挖后要**收回那个结论**：

- 隔离实验证实 Node 语义确实有盲区：`setTimeout` 是宏任务，**不能抢占同步 CPU 工作**。
  纯 Node 复现（预算 300ms + 同步忙等 900ms）→ 定时器一次没触发、`raw` 先赢。
- 但在真实服务里，把预算压到 1s 并用 3000 文件工作区压测，
  **超时每次都仍然生效**（1000ms 预算下 1011~1371ms 就返回错误）——
  因为工具在同步块结束后会立刻 `await`/yield，让定时器抢到。
- `crash.log` 里 `completed AFTER timeout` **0 条**，说明生产上从未出现
  「跑完了才判超时又丢掉结果」。

所以：**这是一个成立但尚未在真实路径触发的机制盲区**，不是已发生的故障。
按「不得为不存在的缺陷改代码」，本轮不动 `mcp-server.js` 的超时逻辑；
把盲区记在这里，等真的出现 `completed AFTER timeout` 再改。

### 3.6 三个写入口的「失败信息质量」不一致 ★本轮修复 F16

这是**重启 opencode 后真机手感实测**发现的（不是错误码统计能看出来的）。

同一件事：`old_string` 打错一个字。各写入口给出的信息完全不同：

| 入口 | 部分失败 | 报错信息 |
|---|---|---|
| `edit_transaction` | 成功的**已落盘** | `failed_edits[]` + `closest_match{line, similarity, snippet}` |
| `code_patch` | 单条 | 只有 `old_string not found in file` |
| `code_batch`（`all_or_nothing=true`，默认） | 整批原子回滚 | 只有 `item_index: N`，无定位信息 |
| `code_batch`（`best_effort`） | 逐文件成功/失败 | `partial_failures[]` 含 file/item_index/code |

补测（同一缺陷的另一面）：`best_effort` 模式本来就有 `partial_failures[]`，
但其中每一级的明细里同样没有 `closest_match` —— 修完 F16 后自动补齐（同一处产出点）。

实测（3 条编辑，第 2 条打错）：

```
# edit_transaction
edits_applied: 2
failed_edits: [{ index:1, error_code:"OLD_STRING_NOT_FOUND",
                 closest_match:{ line:7, similarity:0.6,
                                 snippet:"  return a - b\n}" } }]
→ 只补发那一条即可

# code_batch
{ ok:false, code:"PATCH_OLD_STRING_NOT_FOUND", item_index:1 }
→ 不知道哪条错、错在哪、最接近什么，只能重读整个文件重猜
```

`findClosestMatch` 本来就是 `error-codes.js` 的公共函数（`edit_transaction` 早就在用），
`write-runtime.js` 的 patch 路径只是**没接上**。轨迹里 `PATCH_OLD_STRING_NOT_FOUND`
两池共 **11 次**（`code_batch` 8 / `code_patch` 3），每一次都只能整文件重读。

**修法（F16）**：
1. `write-runtime.js` 单写与批量两处失败点接上同一个 `_patchNotFoundError()`，
   内部调 `findClosestMatch`（单一来源，不各写一份——这正是 F06 幂等判据的教训）。
2. `tools/entry-shared.js` 的 `WRITE_ERROR_DETAIL_KEYS` 补 `closest_match`。
   **这一条是关键**：只改 write-runtime 时 `closest_match` 被白名单静默丢弃，
   实测回包里根本没有——本仓库反复出现的「逐字段白名单重建丢事实字段」同型缺陷。
3. 原子性不动：`code_batch` 仍然整批不落盘（提示信息不得为原子性让路）。

**验证**：`test-patch-not-found-closest.js`（10 断言，含「batch 失败必须整批不落盘」）；
变异 M27（撤白名单）/ M28（不产出 closest_match）均变红（各 4 条）。

### 3.7 跨进程并发写：实测正确，**勿改坏**

两进程各持同一基线并发写同一文件 → 后写者被 `VERSION_CONFLICT` 拒绝，
先写者内容完好，**无静默覆盖**（B 池并发度分布：同时 0 个 665 次、1 个 2 次）。

### 3.8 路由被标识符抢走 ★本轮修复 F17

重启后实测发现的不是「文案难听」，而是**路由判错**：

| goal | 旧结果 | 应为 | 原因 |
|---|---|---|---|
| `document the add function` | change | document | 英文动词全串匹配，函数名 `add` 被当动词 |
| `why does add return empty` | change | diagnose | 同上 |
| `the add function is broken` | change | diagnose | 同上 |
| `为什么不支持并发上传` | change | diagnose | 中文「支持」与名词/标识符同形 |
| `改 alpha 的返回值` | understand | change | 词表只有「修改/改成/改为」，没有裸「改」 |

这不是标签问题：`route=review` 才触发审计完成契约，`route=document` 才展开文档线索。

**修法**：
1. 英文改动动词改句首锚定（允许 `please` / `how do I` 前缀）；句中出现的视为标识符。
2. 「加上/加入/支持」与英文 `error` 降为**弱信号**，只有全无穷强信号时才用。
3. 补裸「改」，但用负向先行断言排除「改动/改进/改善/改期/改天」（「改进」单独列为强信号）。

**验证**：25 断言覆盖 6 个误判、8 个不得回归的真改动目标、evidence 可核查性、
弱信号优先级、default 不编造。变异 M29（撤锚定）/ M30（弱表失效）均变红。

已知保留：`add 这个函数在哪` 仍判 change——纯标识符开头的定位问句，词表里没有「在哪」类信号。
证据会显示 `"add"`，调用方可 `route=understand` 覆盖。不为它加特例词。

### 3.9 检查建议的时机 ★本轮修复 F18

§3.2 量化了「建议太贵且太频繁」，本轮找到了更根本的一层：

```
旧文案：'A prior edit is unvalidated (result_kind=partial): run checks before further edits.'
```

但实现**根本不拦**后续编辑——同一 `read_ref` / `wbase_*` 可以继续写。
一个不存在的前置条件，被当成规则告诉调用方；而轨迹显示真实节奏是
「连写 29.4 次 → 验 1 次」（p90=125）。把可选动作说成必须先做，
只会训练调用方忽略 `next_action`——比不给建议更糟。

**修法**：结构化边保留（`tool` / `args` / `run=true` 照做仍可成），但
1. 未验证状态标 `optional: true`；
2. 文案改为「完成时跑一次」，并明说会跑仓库 test 命令、大仓可能慢；
3. `code_status` 的 `next_step` 同步改口径。
4. **失败路径不变**：上次检查 FAILED 时**不**标可选，仍要求先修再重跑。

**验证**：17 断言（含「FAILED 不得被 optional 吞掉」这条失败路径）；变异 M31/M32/M33/M34 均变红。

### 3.9d 事务提交的 `files_changed` 虚报 ★本轮修复 F19

真机实测（同一个事务）：`a.js` 编辑成功、`b.js` 的 `old_string` 不存在 → commit 回包：

```
files_changed: 2
files: ['src/a.js','src/b.js']      ← b.js 一个字节都没变
stats: [ a.js ]                     ← 只有 1 条
file_hashes: { a.js: … }            ← 只有 1 条
```

同一个回包内部就矛盾：明细都按 `new_hash` 过滤，只有 `files_changed` / `files`
把「事务登记过的文件」当成「改过的文件」（登记发生在尝试编辑之前，供 rollback 用）。
这与 F07（把上限冒充成真实值）同一类：数字说的不是它声称的东西。

**修法**：`files_changed` / `files` 只算真有 `new_hash` 的；登记总数走新增 `files_included`
（不丢信息，不混用）。全失败的事务因此如实回报 `files_changed: 0`。

**验证**：`test-txn-commit-files-changed.js`（15 断言，含全失败路径）；变异 M35（退回登记数）/
M36（删掉 files_included）均变红。

### 3.9b 重启后复验：建议面自洽（F18b）

用户重启 opencode 后，在新进程里真实走了一遍写链，认出两处**只在运行中才看得到**的不一致：

**修法**：成功路径 `allowed_actions` 加入 `code_check`；`next_step` 改为
「先用 `wbase_*` 继续写 → 完成时再跑一次检查」。

**验证**：新增 3 条断言（allowed_actions 含 code_check / next_step 不以 Run code_check 开头 /
保留 write_read_refs 指路）；变异 M33（撤 allowed_actions）/ M34（next_step 退回）均变红。

### 3.9c 本轮见到但**没修**的两件事（记录，不冒充已修）

1. **`state_commit_pending` 的文案在没传 `request_id` 时指向不存在的参数**。

## 3.10 一处公开收回：短标识符不是缺陷

上一轮我在会话里判过「`alpha` 这种 5 字符标识符低于内容扫描 6 字符门槛，
`search_terms` 完全不生效」。**这个判断是错的**，在此收回。

实测（`alpha` 作为真实函数存在的小仓库）：
- `code_task {goal:'改 alpha 的返回值', search_terms:['alpha']}` → **命中** `src/a.js::alpha`；
- 6 字符门槛只作用于**裸文本扫描**（注释/字符串里出现的记号），
  符号检索（`findDefinitions` / `searchSymbols`）从来不看长度；
- 我当时测试的工作区里根本没有 `alpha`，零命中是正确结果。

真实残留仅限：短 token 只出现在注释/字符串、无任何符号时，裸文本扫描会跳过。
这条已有出路（`code_query(mode="search")`），属于**降噪取舍**，不是缺陷。

**仍改了一处文案**：旧提示只说「content scan 被跳过」，读起来像「短 token 完全没用上」
（我自己就被误导了）。现在分开说两条通道，避免后来人重复这个误判。

### F40 `code_patch(create)` 回执 intended hash 为 null（★本轮修复）

### F41 `code_patch` modify 回执 pre/intended 仍为 null（★本轮修复）

真机（重启后 0.6.1，2026-11-05 晚）：`code_patch` modify 不带 `request_id` 时
`receipt.files[0].hashes` 为 `pre=null / intended=null / result=<hash>`；
同一 operation 的 `base_version.file.hash` 与 `result_file_hash` 都有值。
`code_batch` modify 和带 `request_id` 的 `code_patch` 都是 `pre=base / intended=result`，
只有这条常用路径漏账。F40 只修了 create，未覆盖 modify。

修法：`finalOp` 统一补
`pre_file_hash = op?.pre_file_hash ?? base_version?.file?.hash ?? null`、
`intended_file_hash = op?.intended_file_hash ?? r.new_version?.file?.hash ?? null`；
create 的 pre 仍为 null。
